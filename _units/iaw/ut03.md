> **Idea de la unidad:** una conexión que “funciona con root” no está bien resuelta. La aplicación necesita llegar a la base de datos con la identidad, privilegios, esquema y manejo de errores adecuados.

## 1. De la sesión a la persistencia {#persistencia}

En UT02 la identidad podía vivir en una sesión. Ahora necesitamos datos que sobrevivan al cierre del navegador y al reinicio del servicio: usuarios, tickets, tareas o auditoría.

![Cadena PHP-BBDD]({{ '/assets/docencia/iaw/ut03/01_php_db.svg' | relative_url }})

```text
Cliente -> Apache -> PHP-FPM -> aplicación -> PDO -> TCP/3306 -> MariaDB
```

Cada flecha debe poder probarse de forma independiente.

## 2. Preflight antes de culpar al SQL

```bash
php -v
php -m | grep -Ei 'pdo|mysql'
nc -vz 192.168.60.20 3306
mariadb -h 192.168.60.20 -u iawapp_NN -p iawphp_NN -e 'SELECT 1;'
```


El orden importa. Estas pruebas separan preguntas distintas:

```text
¿Existe el driver?       → php -m
¿Llego al puerto?        → nc
¿La identidad SQL entra? → mariadb ... SELECT 1
¿La app usa ese entorno?  → petición HTTP + logs de FPM
```

Si una capa falla, no tiene sentido modificar la siguiente al azar.

Si falta `pdo_mysql`, reescribir la consulta no arreglará `could not find driver`. Si TCP/3306 no responde, tampoco.

## 3. Dos identidades SQL, dos responsabilidades

![Privilegios]({{ '/assets/docencia/iaw/ut03/02_privilegios_db.svg' | relative_url }})

Usaremos dos cuentas:

- `iawmig_NN`: crea/actualiza esquema durante una migración controlada;
- `iawapp_NN`: uso diario de la aplicación, sin `CREATE`, `DROP` ni privilegios globales.

Este diseño permite aplicar mínimo privilegio sin impedir que el despliegue inicialice el esquema.


Como referencia conceptual:

```text
iawmig_NN
  └─ DDL controlado durante despliegue/migración

iawapp_NN
  └─ SELECT / INSERT / UPDATE / DELETE necesarios por la aplicación
```

La cuenta de aplicación no debería disponer de privilegios globales ni de `DROP`/`CREATE` por comodidad.

## 4. PDO y configuración de conexión {#pdo}

```php
$dsn = sprintf(
    'mysql:host=%s;port=%d;dbname=%s;charset=utf8mb4',
    $host,
    $port,
    $database
);

$pdo = new PDO(
    $dsn,
    $user,
    $password,
    [
        PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        PDO::ATTR_EMULATE_PREPARES => false,
    ]
);
```

`ATTR_EMULATE_PREPARES => false` fuerza, cuando el controlador lo permite, el uso de prepared statements nativos. No es una "opción mágica de seguridad": debemos seguir validando datos, autorizando recursos y tratando correctamente los errores.

Las credenciales no deben vivir dentro del `DocumentRoot` ni imprimirse en mensajes de error.

## 5. Crear esquema de forma controlada

RA6.d pide crear bases de datos y tablas utilizando el lenguaje de guiones. Lo haremos mediante una **migración** ejecutada con la cuenta específica, no concediendo DDL permanentemente a la aplicación.

```sql
CREATE TABLE IF NOT EXISTS tickets (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    owner_id BIGINT UNSIGNED NOT NULL,
    title VARCHAR(160) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'open',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_tickets_owner (owner_id)
);
```

La migración puede ejecutarse mediante un script PHP específico usando `iawmig_NN`; la cuenta `iawapp_NN` no necesita conservar permisos DDL después del despliegue.

La migración debe ser repetible o, como mínimo, detectar de forma segura si ya se ejecutó.

## 6. CRUD y consultas preparadas {#prepared}

Nunca concatenes entrada del usuario dentro del SQL.

```php
$stmt = $pdo->prepare(
    'SELECT id, title, status FROM tickets WHERE owner_id = :owner ORDER BY id DESC'
);
$stmt->execute(['owner' => $currentUserId]);
$tickets = $stmt->fetchAll();
```

Las consultas preparadas separan la estructura SQL de los valores.


Para un recurso concreto, la consulta puede incorporar también la autorización por propietario:

```php
$stmt = $pdo->prepare(
    'SELECT id, title, status
       FROM tickets
      WHERE id = :id
        AND owner_id = :owner'
);

$stmt->execute([
    'id' => $ticketId,
    'owner' => $currentUserId,
]);

$ticket = $stmt->fetch();
```

Prepared statement y autorización resuelven problemas **distintos**.

## 7. Seguridad no termina en evitar inyección {#autorizacion}

Aunque una consulta esté preparada, puede existir un fallo de autorización:

```sql
SELECT * FROM tickets WHERE id = :id
```

Si cualquier usuario puede pasar el `id` de un ticket ajeno, la consulta sigue siendo insegura desde el punto de vista de autorización. La consulta debe incorporar el propietario o una regla de permiso equivalente.

## 8. Transacciones {#transacciones}

Cuando dos cambios deben suceder como una única operación, usamos transacciones.

```php
$pdo->beginTransaction();
try {
    closeTicket($pdo, $ticketId, $currentUserId);
    writeAudit($pdo, $currentUserId, 'ticket.closed', $ticketId);
    $pdo->commit();
} catch (Throwable $e) {
    if ($pdo->inTransaction()) $pdo->rollBack();
    throw $e;
}
```

El objetivo no es memorizar tres métodos, sino garantizar consistencia ante un fallo intermedio.


![Transacción: commit o rollback]({{ '/assets/docencia/iaw/ut03/03_transaccion.svg' | relative_url }})

Una prueba útil consiste en provocar un fallo **entre** las dos operaciones y comprobar que no queda un estado parcial.

## 9. Errores que hay que saber distinguir {#diagnostico}

| Síntoma | Capa probable | Primera prueba |
|---|---|---|
| `could not find driver` | PHP / extensión | `php -m` y FPM |
| `Connection refused` | red/escucha | `nc -vz`, `ss -ltnp` |
| `Access denied for user` | identidad/privilegios | login directo + `SHOW GRANTS` |
| `Table ... doesn't exist` | esquema/migración | `SHOW TABLES` |
| 500 sin detalle | aplicación/FPM | logs y excepción |
| `SQLSTATE[42S02]` / tabla ausente | esquema | migración + `SHOW TABLES` |
| datos de otro usuario | autorización | consulta con `owner_id` + sesión |

## 10. Funcionamiento y rendimiento {#rendimiento}

RA6.g exige verificar funcionamiento **y rendimiento**. No convertiremos la UT en optimización avanzada, pero sí aprenderemos a medir antes de opinar:

```bash
curl -sS -o /dev/null -w 'code=%{http_code} time=%{time_total}\n' http://phpdbNN.iaw.test/tickets
```

En MariaDB podemos usar `EXPLAIN` para observar cómo se ejecuta una consulta y justificar índices simples cuando proceda.


Ejemplo:

```sql
EXPLAIN
SELECT id, title, status
FROM tickets
WHERE owner_id = 7
ORDER BY id DESC;
```

No se trata de "poner índices a todo". Primero observamos el patrón de consulta y después justificamos el índice.

## 11. Backups y reversión de cambios de esquema {#backup}

Antes de una migración que pueda afectar datos:

- copia o snapshot conocido;
- exportación lógica cuando proceda;
- migración versionada;
- smoke test;
- plan de rollback.

Una exportación lógica de laboratorio puede realizarse con una identidad específica de backup:

```bash
mariadb-dump \
  -u iawbackup_NN \
  -p \
  iawphp_NN \
  > iawphp_NN.sql
```

Verifica que el fichero no esté vacío y practica una restauración controlada en una base de pruebas. **Una copia que nunca se ha restaurado todavía no demuestra recuperabilidad.**

## 12. Laboratorio guiado: tickets persistentes {#laboratorio}

Partiremos de la miniaplicación de UT02 y añadiremos persistencia sin cambiar su objetivo funcional. El foco está en la integración:

```text
login/sesión
    ↓
usuario actual
    ↓
PDO
    ↓
MariaDB
    ↓
tickets del propietario
```

El laboratorio debe demostrar:

- preflight de driver, TCP e identidad SQL;
- esquema instalado por cuenta de migración;
- cuenta de aplicación con privilegios mínimos;
- DSN y secreto fuera del `DocumentRoot`;
- CRUD mediante prepared statements;
- aislamiento por `owner_id`;
- una transacción con prueba de rollback;
- una medición HTTP y un `EXPLAIN` básico;
- exportación y recuperación controlada;
- diagnóstico de al menos un fallo de integración.
