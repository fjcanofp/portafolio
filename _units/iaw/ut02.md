## 1. Por qué PHP aquí y por qué ahora {#flujo}

Colocar PHP antes de los CMS tiene una ventaja didáctica: cuando más adelante WordPress, Joomla o Nextcloud fallen, el alumno ya sabrá qué son una petición, una variable de servidor, una cookie, una sesión, un formulario POST, una redirección o un error de ejecución. Un CMS deja de parecer magia.

IAW no pretende competir con DWES. La profundidad de programación está al servicio de la **implantación, operación, seguridad y diagnóstico**.

## 2. Cliente y servidor no viven en el mismo sitio

![Flujo PHP]({{ '/assets/docencia/iaw/ut02/01_flujo_php.svg' | relative_url }})

El navegador envía una petición HTTP. Apache selecciona el VirtualHost y deriva los scripts PHP a PHP-FPM. PHP ejecuta código en el servidor y devuelve una respuesta, normalmente HTML. El navegador nunca recibe el código PHP original.

```text
Navegador -> HTTP -> Apache -> FastCGI -> PHP-FPM -> script PHP -> HTML -> navegador
```

Esto tiene consecuencias operativas:

- un error JavaScript se investiga en el navegador;
- un error PHP se investiga en el servidor y sus logs;
- las credenciales no deben imprimirse en HTML;
- una validación HTML5 no sustituye la validación del servidor;
- cambiar `php.ini` de CLI puede no cambiar PHP-FPM.

### CLI y FPM: mismo lenguaje, distinto contexto

Dos ejecuciones de PHP pueden usar configuraciones diferentes:

```text
php script.php
→ PHP CLI

http://phpNN.iaw.test/script.php
→ Apache → PHP-FPM
```

Antes de asumir que "PHP funciona" compara ambos contextos:

```bash
php --ini
php -i | grep -E 'Loaded Configuration|Scan this dir'
systemctl status 'php*-fpm'
```

Un script que funciona por CLI puede fallar mediante FPM por extensiones, permisos, variables de entorno, usuario efectivo o configuración diferente.

## 3. PHP mínimo para un administrador de aplicaciones {#php}

Trabajaremos tipos, variables, operadores, arrays, condiciones, bucles y funciones. No buscamos memorizar el lenguaje: buscamos leer y modificar pequeñas piezas con criterio.

```php
<?php
$usuario = 'ana';
$intentos = 2;

function puedeIntentar(int $n): bool {
    return $n < 5;
}

if (puedeIntentar($intentos)) {
    echo "Acceso disponible para " . htmlspecialchars($usuario, ENT_QUOTES, 'UTF-8');
}
```

La función `htmlspecialchars()` aparece pronto porque una salida dinámica no debe tratar como HTML confiable todo lo que venga del usuario.

## 4. Formularios: entrada no confiable {#entrada-salida}

![Formulario a respuesta]({{ '/assets/docencia/iaw/ut02/02_formulario.svg' | relative_url }})

`GET` resulta útil para filtros y recursos identificables. `POST` suele usarse para acciones que cambian estado o envían información sensible, pero **POST no cifra nada**: la confidencialidad depende de HTTPS.

```php
$nombre = trim($_POST['nombre'] ?? '');
if ($nombre === '') {
    $errores[] = 'El nombre es obligatorio';
}
```

Principio de trabajo: validar en servidor, normalizar lo necesario y escapar al generar salida según el contexto.


### Validar no es lo mismo que escapar

La validación decide si un dato cumple las reglas de entrada. El escape evita que un valor se interprete como código al generar una salida concreta.

```php
$id = filter_input(INPUT_GET, 'id', FILTER_VALIDATE_INT);

if ($id === false || $id === null) {
    http_response_code(400);
    exit('Petición no válida');
}
```

Al producir HTML:

```php
<?= htmlspecialchars(
    $nombre,
    ENT_QUOTES | ENT_SUBSTITUTE,
    'UTF-8'
) ?>
```

```text
VALIDAR entrada
      ≠
ESCAPAR salida
```

La salida debe escaparse **según el contexto**: HTML, atributo, URL, JavaScript o SQL no son el mismo contexto.

## 5. Separar entrada, decisión y salida

Una miniaplicación mantenible evita mezclar todo en veinte líneas dentro de una única plantilla. Aunque no usemos un framework, podemos separar responsabilidades:

```text
public/index.php        punto de entrada
src/                    funciones y lógica de apoyo
templates/              HTML con salida controlada
config/                 configuración no pública
var/                    datos temporales y logs de la práctica
```

La estructura importa porque en producción habrá que decidir qué directorio es público, qué usuario puede escribir y qué se debe respaldar.

## 6. Cookies y sesiones {#sesiones}

PHP ofrece sesiones para mantener datos entre peticiones. Una sesión típica conserva un identificador en el cliente y el estado asociado en el servidor.

```php
session_start();
$_SESSION['user_id'] = 17;
$_SESSION['role'] = 'operator';
```

Tras una autenticación correcta es buena práctica regenerar el identificador:

```php
session_regenerate_id(true);
```

No confundas **autenticación** (quién eres) con **autorización** (qué puedes hacer).


![Sesión, identidad y autorización]({{ '/assets/docencia/iaw/ut02/03_sesion_autorizacion.svg' | relative_url }})

En un entorno HTTPS real también debemos razonar sobre atributos de cookie como `Secure`, `HttpOnly` y `SameSite`. El objetivo no es memorizar una combinación universal, sino saber qué riesgo reduce cada atributo.

Tras autenticarse, la identidad debe proceder de una fuente controlada por el servidor. Un parámetro `?user_id=17` enviado por el navegador no es una identidad confiable.

## 7. Autenticación: nunca almacenar contraseñas en claro {#auth}

PHP proporciona `password_hash()` y `password_verify()` para almacenar y verificar hashes de contraseña.

```php
$hash = password_hash($password, PASSWORD_DEFAULT);

if (password_verify($passwordIntroducida, $hash)) {
    // credencial correcta
}
```

En esta UT usaremos un almacén didáctico de usuarios suministrado por el profesor; la persistencia real en MariaDB llegará en UT03.

## 8. Autorización y aislamiento

Un usuario autenticado no debe poder ver los recursos de otro simplemente cambiando un parámetro.

```php
// INCORRECTO: confiar en ?user_id=...
$id = (int)($_GET['user_id'] ?? 0);

// MEJOR: identidad derivada de la sesión
$id = (int)$_SESSION['user_id'];
```

El objetivo del CE RA5.i es demostrar que el entorno de cada usuario queda aislado. Una prueba válida incluye dos identidades y un intento negativo.


Una prueba completa debería demostrar tres cosas:

1. el usuario A accede a su recurso;
2. el usuario B accede al suyo;
3. A no puede obtener el recurso de B manipulando una URL, formulario o identificador.

> **Regla:** una interfaz que oculta un botón no constituye autorización. La comprobación debe producirse en el servidor.
{: .notice--warning}

## 9. CSRF, XSS e IDOR: tres ideas que hay que reconocer {#seguridad}

- **XSS:** datos no confiables terminan interpretándose como código/HTML en el navegador.
- **CSRF:** un navegador autenticado es inducido a enviar una acción no deseada.
- **IDOR:** el usuario manipula un identificador y accede a un recurso que no le pertenece.

No haremos explotación ofensiva. Diseñaremos pruebas defensivas y verificaremos que la aplicación rechaza acciones no autorizadas.


### Patrón defensivo mínimo frente a CSRF

Para acciones que cambian estado, una aplicación con sesión puede asociar un token impredecible a la sesión y comprobarlo al recibir el `POST`. En esta unidad nos interesa comprender el patrón, no construir una librería de seguridad completa.

```text
formulario legítimo
      ↓ incluye token
servidor compara token recibido ↔ token de sesión
      ├─ coincide → procesa
      └─ no coincide → rechaza
```

## 10. Diagnóstico de PHP {#diagnostico}

Orden recomendado:

```bash
php -v
php --ini
php -m
php -l fichero.php
systemctl list-units 'php*-fpm.service'
systemctl status 'php*-fpm.service'
journalctl -u 'php*-fpm.service' --since -10min
```

Desde cliente, completa la evidencia con HTTP real:

```bash
curl -i http://phpNN.iaw.test/
curl -i -X POST \
  -d 'nombre=Ana' \
  http://phpNN.iaw.test/formulario.php
```

No basta con que el proceso FPM esté activo: Apache debe enviarle la petición, el script debe ejecutarse y el cliente debe recibir la respuesta esperada.

Y recuerda: el `php.ini` de CLI y el de FPM pueden ser diferentes.

## 11. Procedimiento profesional

1. reproducir el síntoma;
2. decidir si el fallo está en cliente, Apache, FPM o script;
3. revisar el error exacto;
4. aislar el caso mínimo;
5. cambiar una sola causa plausible;
6. repetir la prueba;
7. probar un caso negativo;
8. documentar el resultado.

## 12. Laboratorio guiado: miniaplicación sin base de datos {#laboratorio}

Construiremos una miniaplicación deliberadamente pequeña para que el foco siga siendo IAW:

```text
/var/www/phpNN/
├── public/
│   ├── index.php
│   ├── login.php
│   ├── area.php
│   └── logout.php
├── src/
│   └── auth.php
├── templates/
└── var/
```

La aplicación debe permitir observar y justificar:

- qué ejecuta el navegador y qué ejecuta PHP;
- procesamiento `GET`/`POST`;
- validación y escape;
- creación, regeneración y cierre de sesión;
- autenticación con hash;
- autorización de una zona privada;
- dos usuarios con aislamiento;
- un caso negativo documentado;
- diagnóstico mediante logs, HTTP y `php -l`.

No se exige persistencia SQL: esa responsabilidad comienza en UT03.
